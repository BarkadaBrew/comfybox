codex
Neither spec is build-ready as written. The storage spec has four blockers around data integrity, render races, HF cache topology, and foreign-tree confinement. The variable-size addendum has two blockers around packing and admission-cost semantics. The underlying product directions are sound.

## Models storage tiers

1. **BLOCKER — The move protocol is not loss-safe.** A `≥95%` size comparison permits substantial truncation, and `rm → symlink` is not atomic: interruption can leave the serving path absent or pointed at an incomplete destination. Require a temporary destination, successful rsync exit, exact per-file manifest verification or hashes, destination flush/rename, and an atomic hot-path swap backed by a durable recovery journal. [§ Safety rules](/Users/toddwalderman/Projects/zimage.swift/specs/models-storage-tiers.md:55)

2. **BLOCKER — There is no render/move exclusion contract.** “Paced off-render” only governs job start. A render can resolve or enqueue the item after the move guard passes, or while copying, then reach the path during commit. Introduce an item-scoped lifecycle lease shared by every render resolver and storage job. Loads during copy may continue from the old path; commit must recheck queued/running/loaded references under that lease. Define whether a request blocks, cancels the move, or fails when its item is queued for archive/delete. [§ Safety rules](/Users/toddwalderman/Projects/zimage.swift/specs/models-storage-tiers.md:46)

3. **BLOCKER — “Item” is undefined for HF repositories.** Z-Image and similar models are multi-directory packages containing configs, tokenizer state, indexes, and sharded weights; HF snapshots also symlink into potentially shared `blobs/`. The existing nearline scan sees individual `.safetensors`, which cannot safely represent or move a loadable model. Define item manifests and ownership boundaries for logical models, components, snapshots, shared blobs, and single-file LoRAs. “Dedup is a non-goal” cannot permit breaking shared snapshot references. [§ Tiers](/Users/toddwalderman/Projects/zimage.swift/specs/models-storage-tiers.md:31), [§ Non-goals](/Users/toddwalderman/Projects/zimage.swift/specs/models-storage-tiers.md:96)

4. **BLOCKER — Foreign-tree protection lacks enforceable path rules.** A `managedBy` label is insufficient for destructive operations when configured roots or symlinks can traverse into LM Studio or another manager’s tree. Mutation must use canonicalized, no-follow paths; allowlisted managed roots and volume identities; catalog ownership checks; and a final pre-commit containment check. Archive deletion must reject symlinks and delete only the catalog-owned real object. [§ Safety rules](/Users/toddwalderman/Projects/zimage.swift/specs/models-storage-tiers.md:52)

5. **MAJOR — Existing “nearline” semantics conflict with the new tier.** Today `NearlineLibrary` treats attached storage as the authoritative source, copies requested items back to a local staging cache, and LRU-evicts those copies. The new spec defines nearline as a directly loadable symlink into Bolt. Without a migration/compatibility contract, auto-stage can silently promote nearline items back online and old eviction routes can act on the wrong representation. Define replacement behavior for `/v1/nearline/*`, persisted state migration, and old clients. [§ Prior art](/Users/toddwalderman/Projects/zimage.swift/specs/models-storage-tiers.md:18), [§ Tiers](/Users/toddwalderman/Projects/zimage.swift/specs/models-storage-tiers.md:31)

6. **MAJOR — Filesystem truth does not by itself yield stable identity or a unique tier.** During a move an item exists in two locations; duplicate filenames may exist across roots; a broken link and an archived item may have similar observable states. The current nearline catalog uses a bare filename and “first root wins.” Define a stable logical ID—such as manager, package/component identity, and content identity—plus multiple placements, precedence rules, catalog revisions, and reconciliation ownership with the asset catalog service. [§ Tiers](/Users/toddwalderman/Projects/zimage.swift/specs/models-storage-tiers.md:40), [§ API](/Users/toddwalderman/Projects/zimage.swift/specs/models-storage-tiers.md:76)

7. **MAJOR — The transition state machine is incomplete.** Specify allowed edges and postconditions for online↔nearline, nearline↔archive, online→archive, restore-to-online, and delete. Add transient states such as `copying`, `verifying`, `committing`, `failed`, and `recoveryRequired`; serialize same-item jobs; and define retry/cancel behavior. `delete` is a terminal action rather than a filesystem-derived tier unless tombstones remain cataloged. [§ Tiers](/Users/toddwalderman/Projects/zimage.swift/specs/models-storage-tiers.md:31), [§ API](/Users/toddwalderman/Projects/zimage.swift/specs/models-storage-tiers.md:81)

8. **MAJOR — Offline status is underspecified and absent from the API DTO.** When Bolt disappears, the catalog must retain last-known items and distinguish “root inaccessible” from “item absent”; otherwise a scan can erase entries or misclassify them. `availability/offline` should be orthogonal to tier, with root health and link-target diagnostics. Validate at load time as well as startup/mount events, and prohibit archive/delete/reconciliation commits while any required root is inaccessible. [§ Safety rules](/Users/toddwalderman/Projects/zimage.swift/specs/models-storage-tiers.md:58), [§ API](/Users/toddwalderman/Projects/zimage.swift/specs/models-storage-tiers.md:78)

9. **MAJOR — Pin coverage and the nearline latency acknowledgement are not server-enforceable.** The dependency set must include queued and reserved renders, active loaders, presets resolved through aliases, dynamic LoRAs, and every relevant process’s launch/config state—not only the loaded pool. Because krea2 incurs its 65-second reload repeatedly, nearline demotion should require a server-minted, expiring acknowledgement tied to the item and catalog revision; an API or bulk caller must not bypass the UI warning. Return resolved dependents and latency reasons in `allowedTransitions`. [§ Safety rules](/Users/toddwalderman/Projects/zimage.swift/specs/models-storage-tiers.md:46)

10. **MAJOR — “Existing job polling” is not a usable storage-job contract.** Existing image/video status trackers are type-specific, in-memory, and short-lived. Define a storage-job endpoint and durable DTO with item ID, source/target, phase, byte/file progress, timestamps, error, restart reconciliation, cancellation boundary, retry policy, and terminal result. Move submission also needs idempotency and expected-catalog-version fields to prevent double moves and stale UI actions. [§ API](/Users/toddwalderman/Projects/zimage.swift/specs/models-storage-tiers.md:81), [§ UI](/Users/toddwalderman/Projects/zimage.swift/specs/models-storage-tiers.md:88)

11. **MAJOR — Root configuration and capacity admission are missing.** “Registered move targets” needs API/schema support for root role, nearline/archive directories, writable/read-only capability, stable volume UUID, manager ownership, and preferred online destination. Before copying, admit against destination free space plus safety headroom; restores must likewise protect the home watermark. Define partial-copy cleanup and reject source/target aliases or same-location moves. [§ API](/Users/toddwalderman/Projects/zimage.swift/specs/models-storage-tiers.md:85), [§ Signals](/Users/toddwalderman/Projects/zimage.swift/specs/models-storage-tiers.md:73)

12. **MAJOR — Delete confirmation is incomplete at the protocol boundary.** The spec requires a “confirm token” but defines neither issuance nor transport. Mint a short-lived token after server-side preflight, scoped to item ID, content identity, path, catalog revision, and typed name; consume it once and repeat all guards immediately before deletion. Audit both refusal and success with actor, bytes, canonical path, and content identity. [§ Safety rules](/Users/toddwalderman/Projects/zimage.swift/specs/models-storage-tiers.md:62), [§ API](/Users/toddwalderman/Projects/zimage.swift/specs/models-storage-tiers.md:84)

13. **MINOR — `last-used` cannot be joined reliably from current signals.** Trace `config` is free-form text, filenames and paths change across moves, and usage counts do not necessarily provide a last-used timestamp. Emit structured storage item/content IDs into render traces, define which lifecycle event counts as use, preserve usage across relocation, and distinguish never-used from unknown/unresolvable. Otherwise suggestions will be noisy, though v1’s suggestion-only policy limits harm. [§ Signals](/Users/toddwalderman/Projects/zimage.swift/specs/models-storage-tiers.md:66)

## Kira Rev 3: Variable video size

14. **BLOCKER — Per-reservation greedy “largest rung that fits” can break the lineup.** If the first reservation consumes a large rung, later reservations may not fit even though a smaller first rung would let all minimum rungs run. This contradicts “never dropped slots.” Define global packing: reserve minimum acceptable rungs for mandatory reservations first, then allocate upgrades by priority/quality utility; if even minima do not fit, use Rev 2 push/quarantine rules explicitly. [§ Scheduler behavior](/Users/toddwalderman/Projects/zimage.swift/specs/kira-reservation-scheduler.md:394)

15. **BLOCKER — A scalar measured cost per rung regresses Rev 2’s admission contract.** The measured duration/resolution/steps/refine relationships are sound, but fitting must use the complete conservative P95 execution signature: seed generation, VLM attempts, model residency, eviction/reload—including krea2’s 65-second reload—drains, refine, decode, and transition costs. A rung estimate may be the UI baseline, not the sole protected-window admission value. [§ Mechanism](/Users/toddwalderman/Projects/zimage.swift/specs/kira-reservation-scheduler.md:381), [§ Scheduler behavior](/Users/toddwalderman/Projects/zimage.swift/specs/kira-reservation-scheduler.md:396)

16. **MAJOR — Rung geometry is not the geometry the engine necessarily renders.** `480p/720p` lacks orientation and exact dimensions; current I2V treats requested dimensions as an area budget, then source aspect and `/64` snapping determine actual dimensions. Two-stage behavior can also change final output size around its floor. A reservation must persist nominal budget, resolved stage-one geometry, final geometry, frames, and fps after its source is known; cost, memory, and delivery checks must use those resolved values. [§ Mechanism](/Users/toddwalderman/Projects/zimage.swift/specs/kira-reservation-scheduler.md:383)

17. **MAJOR — “Largest” has no defined ordering.** Resolution, duration, and steps are independent quality dimensions: 1080p/5s and 720p/12s are not naturally comparable. Give each MediaType an explicitly ordered set of stable rung IDs with a revision, minimum acceptable rung, quality/utility ordering, eligibility predicates such as `idleOnly`, and complete engine-valid parameters. Speech/refine variants need distinct signatures rather than an informal multiplier. [§ Mechanism](/Users/toddwalderman/Projects/zimage.swift/specs/kira-reservation-scheduler.md:381)

18. **MAJOR — Downshifting conflicts with immutable reservations and durable dispatch.** “In-flight-adjacent” must be defined precisely. A rung may change only while still reserved/daemon-queued and before dimension-dependent seed, optimization, or QA work begins; it cannot mutate after `dispatching`, `engineQueued`, or `running`. Use a revision-checked amendment or replacement attempt and persist the selected rung and reason atomically. Manual/fixed-rung or campaign-minimum reservations must be non-shrinkable. [§ Scheduler behavior](/Users/toddwalderman/Projects/zimage.swift/specs/kira-reservation-scheduler.md:399)

19. **MAJOR — No stabilization or quality-fairness policy prevents rung thrash and starvation.** Replanning around small timing or estimate changes can alternate a reservation between adjacent rungs, while repeated interactive bumps can permanently prevent top rungs. Add a freeze horizon, downgrade hysteresis, monotonic downgrade within a slot, and controlled upgrade cutoffs. Track quality debt or age so eligible top/idle rungs eventually receive capacity rather than always losing to throughput. [§ Scheduler behavior](/Users/toddwalderman/Projects/zimage.swift/specs/kira-reservation-scheduler.md:396)

20. **MAJOR — Time fit is not sufficient for governor admission.** Each rung also needs conservative peak-memory, resource, preemption, and uninterruptible-phase estimates. Specify what happens when a time-selected rung fails memory/phase admission at dispatch: atomically downgrade and re-fit, defer, or quarantine. It must never silently enter the engine queue or consume a protected window while retrying. [§ Scheduler behavior](/Users/toddwalderman/Projects/zimage.swift/specs/kira-reservation-scheduler.md:394)

21. **MAJOR — The Telegram formula is only an estimate, not a cap.** Variable bitrate, audio, container overhead, and encoder variance can exceed the predicted size. Define a conservative byte budget with headroom, encoder bitrate/max-rate behavior, actual post-encode byte validation, and a bounded fallback such as transcode or delivery-rung downgrade. Record the delivered encoding separately from the render rung. [§ Scheduler behavior](/Users/toddwalderman/Projects/zimage.swift/specs/kira-reservation-scheduler.md:401)

22. **MAJOR — The addendum defines no shared ladder API.** Extend the versioned schedule config with ladder/rung IDs, ordering, revision, exact parameters, eligibility, delivery cap, cost-estimate version/confidence, and memory estimate. Ledger/queue DTOs need selected rung, selection reason, alternatives, and whether it remains mutable. Motion must fetch the same server-owned ladder and submit a rung ID plus revision; hard-coded S/M/L values would immediately create catalog drift between manual and scheduled paths. [§ Pre-#23 quick wins](/Users/toddwalderman/Projects/zimage.swift/specs/kira-reservation-scheduler.md:405)

## Build-readiness verdicts

- **Models storage tiers: NOT READY / BLOCKED.** Resolve findings 1–4 before implementation. Findings 5–12 should be folded into the server contract and state-machine design before P1/P2 estimation is retained.

- **Kira Rev 3 addendum: NOT READY / BLOCKED, with sound direction.** Size ladders are the right abstraction, but the global selection algorithm and conservative admission-cost contract must be specified first. Findings 16–22 should land in the addendum and its versioned API schema before scheduler or Motion UI work begins.
